# Issue #1：输入框与字段绑定方案

状态：**讨论稿，尚未开始功能开发**。更新时间：2026-10-13。代码基线：`20cfd4e`。

需求来源：[指定输入框升级 #1](https://github.com/selfkit/switchboard/issues/1)。

用户希望在网页上选择一个输入框，再把它与左侧某个填写值绑定；下次打开时可以按绑定赋值。
后续会在**独立项目**里建设自动化测试，本项目的这项功能为其提供设计与协议参考。本轮只完成可行性分析和文档。

## 1. 可行性结论

**可行，现有 Tauri + 页面注入架构可以继续使用，但需要升级绑定模型和执行协议。**

已有的元素点击捕获、选择器生成、跨帧通信、React/Vue 输入事件适配、加密存储都能利用。
主要工作不是多加几个填写按钮，而是让每一条绑定准确回答：

| 问题 | 需要保存或执行的内容 |
| --- | --- |
| 在哪里填 | 页面匹配条件、iframe / Shadow DOM 路径、元素定位条件 |
| 从哪里取值 | 账号字段或附加字段的稳定引用，执行时才读取当前值 |
| 什么时候填 | 手动执行或允许自动填写；等待目标可用、限定执行期限 |
| 填得怎样 | 每条绑定的结果、失败原因、取消状态；不能只显示“脚本已发送” |

建议首版完成“任意支持的输入框 ↔ 账号字段”的可靠闭环。后续测试项目复用定位与赋值协议，自行加入点击、断言、用例编排、报告和 CI。
这能避免测试项目被当前侧栏布局、Tauri IPC、账号库格式和登录态存储绑定。

### 本轮讨论中的默认建议

以下两项已向用户征询，**尚未视为确认**。本文暂按建议方案展开，收到意见后修订：

1. 新绑定默认属于“当前账号 + 当前页面”；平台共享模板作为后续能力。原有平台账号/密码适配继续兼容。
2. 每条绑定可选“自动填写 / 仅手动执行”。账号、密码新建绑定建议默认自动；TOTP 和附加字段默认手动，可自行开启自动。

其他建议：先选网页输入框，再在左侧选择值来源；只绑定账号、密码、实时 TOTP 和附加字段，不新增通用脚本或业务流程编辑器。

## 2. 当前实现与需要补齐的部分

以下是代码中已经存在的行为，不代表本方案已经实现。

| 当前能力 | 代码位置 | 对本需求的影响 |
| --- | --- | --- |

| 每个 frame 注入 agent，主文档广播定位请求，再定向传值 | [adapter.rs](../src-tauri/src/adapter.rs) 的 `agent_js` | 有基础，但当前自动填充要求同一帧同时找到账号和密码，且先认领者获胜 |
| agent 中 `waiting` 是单个共享槽，回传没有实际填入后的结构化结果 | 同上 | 多绑定并发容易串任务；需要任务关联、顺序执行和完成回执 |
| 自动填充只在首个页签开启；有同站检查和 2 分钟窗口，agent 再等待元素约 30 秒 | [session.rs](../src-tauri/src/session.rs) 的 `build_tab`；[adapter.rs](../src-tauri/src/adapter.rs) 的 `autofill` | 新绑定要按页面和页签执行，并明确 SPA、刷新与超时语义 |
| 锁定时保活页面可以继续存在；账号库已经关闭 | [lib.rs](../src-tauri/src/lib.rs) 的 `lock_down`；[session.rs](../src-tauri/src/session.rs) 的 `keep_alive` | 页面继续运行不等于允许继续取密码；待执行的绑定必须取消 |

## 3. 首版范围

| 能力 | 首版建议 |
| --- | --- |
| 账号、密码、TOTP、任意附加字段绑定 | 支持；保存字段引用，修改值后绑定自动使用新值 |
| 单条执行、当前页“按绑定填写” | 支持；逐条显示结果 |
| 下次打开自动填写 | 按绑定开关执行，仅匹配已确认页面 |
| 一个值对应多个输入框 | 支持分别建立绑定；同一目标不能自动应用多个不同值来源 |
| 重命名、重排附加字段 | 绑定保持；删除字段后明确显示失效，不能指向旁边的字段 |
| 多步骤登录 | 每个页面分别建立绑定；用户点击“下一步”后，符合条件的新页面可填；首版不自动点击“下一步” |
| 标准文本类 input、password、textarea | 支持；值不被控件接受时报告失败 |
| 同源、同站跨源 iframe，open Shadow DOM | 支持目标；跨帧定位必须先通过技术验证，见第 11 节 |
| 外部身份提供方等跨站 iframe | 首版不自动放行；提示该上下文暂不支持，保持当前同站限制 |
| select、checkbox、radio、文件上传、富文本编辑器 | 后续扩展，各自需要独立动作和验证语义 |
| closed Shadow DOM、Canvas 软键盘、只接受真实键盘事件的控件 | 首版不承诺支持；保留现有手动填充/复制兜底 |
| 图形验证码、短信验证、扫码 | 用户处理；TOTP 仅指账号中已有密钥生成的动态码 |
| 自动登录提交、跨页面流程、断言、录制回放、测试报告、CI | 由未来独立自动化项目设计 |
| 从外部进程控制 Switchboard、开放 HTTP/CDP 服务 | 本期不建立；以后若需要另立接口方案 |

字段自动输入本身可能触发网站的自动提交或联动请求。因此“没有执行点击提交”不代表页面绝无业务副作用，尤其是验证码、搜索和自动保存表单。

## 4. 用户操作流程

### 创建绑定

1. 在当前账号下打开目标网页，点击“绑定输入框”。
2. 用户在网页里点击一个支持的输入框；页面只高亮选中的框，不读取或保存它当前的值。
3. 左侧显示待绑定元素，列出可选来源：账号、密码、验证码、各附加字段。敏感值只显示字段名和打码提示。
4. 用户选择来源，查看适用页面，选择是否自动填写。
5. 点击“保存”仅保存；点击“保存并试填”保存后执行一次，并显示实际结果。

左右选择也可以反过来作为快捷入口：某字段旁点击“绑定”，再去网页点框。两条入口最终走同一套草稿与保存流程。
配置区放在侧栏或为其让出原生 WebView 空间，不能用覆盖在网页上方的普通 React 弹层，避免被原生子 WebView 遮挡。

### 后续使用

每个字段旁可显示“未绑定 / 已绑定 / 需要重新指认”，并提供执行、重新指认、停用、删除。
账号下提供“当前页绑定”列表和“按绑定填写”。先按页面筛选，再顺序执行；每条结果单独展示。
绑定关联稳定页签标识，操作途中切换账号或页签不会把值填到新激活的页面。

指认过程在取消、超时、页签关闭、导航、锁库时结束。已有绑定不因取消修改而丢失。
建议指认期限为 60 秒；重新指认成功前保留原配置，保存新配置时替换。

## 5. 数据模型与定位语义

### 5.1 三个独立概念

- **ElementTarget**：页面范围和元素位置，不包含账号值。
- **ValueRef**：执行时从当前账号哪里读取值；不复制密码或 TOTP 到绑定记录里。
- **FieldBinding**：把 target 与 valueRef 关联，并指定填写策略。

下面是协议讨论样例，字段名尚未冻结，不是现有 API：

```json
{
  "schemaVersion": 1,
  "id": "binding-uuid",
  "accountId": "account-uuid",
  "label": "企业编号",
  "enabled": true,
  "valueRef": {
    "kind": "extra",
    "fieldId": "extra-field-uuid"
  },
  "target": {
    "page": {
      "origin": "https://console.example.com",
      "pathname": "/login",
      "hashRoute": null,
      "queryEquals": {}
    },
    "contextPath": [
      {
        "kind": "frame",
        "locator": { "kind": "css", "value": "iframe#login-frame" },
        "origin": "https://passport.example.com",
        "pathname": "/login"
      },
      {
        "kind": "shadow",
        "locator": { "kind": "css", "value": "tenant-login" }
      }
    ],
    "locator": { "kind": "css", "value": "input[name=tenantCode]" },
    "expected": { "tag": "input", "type": "text" }
  },
  "fill": {
    "trigger": "manual",
    "overwrite": "empty-only",
    "events": ["input", "change"]
  }
}
```

`valueRef` 首版只支持以下明确分支：

| kind | 其他字段 | 解释 |
| --- | --- | --- |
| `account` | `field: username` 或 `field: password` | password 由后端映射到现有 `credential` |
| `totp` | 无 | 目标可填写时现算验证码，不保存动态码或密钥副本 |
| `extra` | `fieldId` | 从这个账号的附加字段按稳定 ID 获取 |

敏感性从当前字段类型和 `secret` 标记派生，绑定导入不能自行把密码降级为非敏感。
首版不引入 JS 表达式、任意脚本或写在配置中的明文密码。

### 5.2 页面匹配

新绑定默认精确匹配 origin（协议、主机、有效端口）与 pathname；路径大小写、尾斜杠不擅自归一成同一页。
SPA 使用 hash 路由时，保存明确的路由部分。普通锚点不当路由；遇到包含临时令牌的 hash 需先整理为可确认的页面条件。

`queryEquals` 中的键值必须全部匹配，其余查询参数不参与判断。空对象表示不限制 query；UI 必须把这个范围讲清楚。
如果站点靠 `mode=reset` / `action=login` 等查询参数区分登录和修改密码，开启自动填写前必须添加相应条件；无法确认页面范围时先用手动模式。
不保存 OAuth code、token、state 等动态凭据，也不把带凭据的完整 URL 写进日志或导出文件。

同平台、同域名和“在这个账号下打开”都不能单独作为填写授权。
页面重定向到另一个登录 origin 时需要在那里重新确认绑定；首版不提供泛域名通配自动填写。

### 5.3 元素匹配

`contextPath` 是从顶层 document 到目标所在 root 的有序路径，frame 与 shadow 步骤可以交错。
每个 frame 步骤定位宿主 iframe，并验证子文档实际 origin/path；每个 shadow 步骤进入对应宿主的 open shadowRoot。
它比把 iframe、Shadow DOM 分成两组数组更能表达“Shadow DOM 内嵌 iframe”等结构。

首版正式执行的 locator 只定义 CSS。可以采集 label、role、placeholder、test id 作为展示和候选信息，
但在没有实现其精确匹配语义前，不能把它们宣称为可执行 locator。未来增加 kind 时需要声明能力与版本。

生成 CSS 时优先稳定 id、name、明确属性，正确转义；结构路径仅作兜底，提示更容易受改版影响。
不把框内值、token、动态敏感属性拼进选择器。
每一步上下文和最终目标都必须唯一；元素选择以指定 root 为边界，不再递归搜索所有 shadow root 后取第一个。
最终候选需要是支持的、可见且可编辑的字段，并核对 tag/type；零命中等待到期限，多命中明确失败，不能用 first/nth 猜一个。

同一个页面上重复出现同名 iframe 时，单凭 origin 不够；必须确认父 frame 中的 iframe 元素路径。
跨源 iframe 无法直接读取父文档 DOM，应由父子 agent 逐层握手组装路径，并用 `event.source` 对应具体 iframe。
window/frame 对象引用只用于当前文档，不能序列化后当作下次仍然有效的地址。

Playwright 的官方定位文档也强调稳定定位与多命中失败；这里借鉴的是这些原则，本文的 CSS root 语义不等同于 Playwright 默认穿透 Shadow DOM 的行为。
独立执行器必须显式实现这个差异。[参考：Locators](https://playwright.dev/docs/locators)

### 5.4 附加字段稳定 ID

`ExtraField` 增加稳定 `id`。旧数据在解锁后的 `db::prepare` 阶段以事务补齐并写回，重复解锁不重新生成。
改 label、值、敏感标记或排序时保留 id；新建字段生成新 id，删除后原绑定变为 `missing_source`。

需要同步修改编辑表单、保存校验、打码恢复和复制账号：`unmask` 改按 id 匹配，拒绝重复或错误归属的 id；不能继续用 label 或数组下标恢复敏感值。
复制新建账号时为附加字段生成新 id；首版默认不复制绑定。未来增加“连绑定一起复制”时显式重映射 id。

## 6. 执行过程与回执

一次执行由后端创建 `runId`，绑定具体账号、稳定 webview label、导航代次 `documentId`、绑定列表和截止时间。
页面不得通过回传自选 accountId 或值来源。相同页面同一时刻只运行一组绑定，组内顺序执行，避免焦点与框架联动互相干扰。

建议执行顺序：

1. 验证账号库已解锁、会话没有被区域拦截、目标页签存在。
2. 验证顶层 URL 与 frame 路径，定位唯一的可编辑目标；这一阶段不传值。
3. 目标就绪后，后端重新核对 run、文档和来源有效性，读取当前字段值；TOTP 在这时生成。
4. 向已经确认的目标上下文定向发送本条值，使用原生 setter 和指定事件。
5. agent 在短暂的渲染稳定期后核对值是否仍在目标里，只回传接受/拒绝状态，不回传值。
6. 后端接收有效回执，更新该条结果，然后执行下一条；总期限内结束。

自动模式建议只填空框，已有相同值返回 `already_matches`，已有不同值返回 `nonempty_skipped`。
用户主动执行时可明确选择覆盖；不能在后台悄悄覆盖用户刚输入的内容。
不使用剪贴板作为自动填写步骤；现有“手动填写并复制”仍是独立入口。

### 生命周期约束

| 场景 | 处理建议 |
| --- | --- |
| 元素异步出现 | 有界等待，建议整组默认 30 秒；不能无限轮询 |
| 用户明确打开或刷新页面 | 启动最长 120 秒的自动填写许可窗口，匹配成功的绑定每个文档只执行一次 |
| SPA 路由改变 | 检查新 route、使旧任务失效；仅在现有许可窗口内启动匹配任务，不无限续期 |
| iframe 重载或跳转 | 旧 frame 引用与回执失效；重新发现时从完整路径校验开始 |
| 页面重渲染、目标被替换 | 定位阶段可重试；已经发送值却没有回执时不能直接再写，先检查当前状态 |
| 锁库、关闭会话、区域切断 | 取消待执行任务，清理排队值，迟到回执不能推进后续步骤 |
| 取消时已写入一部分字段 | 返回 `cancelled` 与逐条结果；已触发的网站事件无法撤销，不能承诺回滚 |
| Issue #2 的保活刷新 | 继续维持页面，但不新开自动赋值许可窗口；锁库期间绝不获取新密码/TOTP |
| 解锁后仍有保活页面 | 不恢复锁定前排队的任务；用户手动执行或下一次明确打开/刷新后再填 |
| TOTP 即将过期 | 建议剩余不足 5 秒时等待下一周期，仍受执行期限约束；不能把旧验证码长期排队 |

现有 `renav()` 同时重置自动填充时钟，实现时需要区分“用户刷新、保活刷新、区域恢复”等导航原因，不能所有刷新都重新授权新绑定。
异步脚本中已经发出的操作无法被后端瞬间收回；应缩短传值到写入的间隔，并由 agent 在每次写入前再检查取消和文档状态。
目标网页本来就能读取填写到自己输入框里的值，本方案不承诺对抗目标站点自身的恶意代码。

### 结果约定

建议运行终态：`completed`、`partial`、`failed`、`cancelled`。`completed` 表示每条要求的填写已完成或值本就一致；跳过、错误不能混为完成。

建议每条结果包含 `runId / bindingId / documentId / status / code / durationMs`，不包含字段值、验证码、DOM 全文或敏感 URL。
首版至少区分：

| code | 含义 |
| --- | --- |
| `filled` / `already_matches` | agent 观察到赋值被目标接受 / 已是期望值 |
| `nonempty_skipped` | 自动模式没有覆盖已有不同值 |
| `target_not_found` / `ambiguous_target` | 等待后仍无目标 / 存在多个候选 |
| `unsupported_target` / `value_rejected` | 控件不支持 / 值被清空、转换或拒绝 |
| `missing_source` / `empty_source` | 字段引用失效 / 当前没有可填写值 |
| `page_mismatch` / `frame_mismatch` | 顶层页面或子 frame 不匹配 |
| `vault_locked` / `session_cut` | 锁库或区域策略阻止执行 |
| `stale_document` / `cancelled` / `timeout` | 文档变了、被取消或执行期限已到 |
| `unsupported_schema` / `unsupported_capability` | 当前执行器不能理解该配置 |

这些回执是页面执行结果，可能被页面脚本伪造，不能成为安全授权依据。
`filled` 只说明输入框层面的接受，不证明已登录、提交成功或服务器保存成功；独立测试项目须另做业务断言。

## 7. 存储、兼容与导入导出

建议在现有 SQLCipher 库中新增 `field_bindings` 表，包含 binding id、account id、schema version、配置 JSON、更新时间。
账号删除时在同一事务里删除绑定，不能依赖未启用的 SQLite 外键级联。普通加密备份携带绑定，继续排除 cookie 快照。
绑定保存与账号字段 ID 迁移都在成功解锁之后执行，不在密码预检或区域检查前写库。

原有 `PlatformConfig` 作为旧格式保留，运行时转换为只包含 username/password 的兼容配置；暂不破坏现有导入导出。
旧配置没有完整 frame/page 信息，不能凭空标记成新的精确绑定，也不能给它扩展到附加字段的自动权限。

一个账号启用新的绑定配置后，**该账号统一使用新执行器**，停止旧平台自动填充，避免两个执行器抢写。
UI 要显示这种切换，并允许从旧账号/密码配置生成待确认草稿；用户可选择回到旧平台适配。
新配置暂时找不到目标时明确报错，不能悄悄回落旧逻辑去另一个表单填写。
旧版 JSON 继续走原入口；新版配置使用版本化入口，不能让旧导入器误解析并覆盖平台配置。

新绑定作为独立文件导出时，建议只导出 target、策略和逻辑输入名，不导出 accountId、账号数据、密码、TOTP 密钥、当前验证码、cookie 或 localStorage。
导入先完整校验版本、结构、来源映射与重复项，再原子保存。导入的自动填写开关默认关闭，用户核对页面和来源后再启用。

## 8. 为独立自动化测试项目保留的边界

### 8.1 可以参考或复用什么

| 内容 | Switchboard 负责 | 独立测试项目负责 |
| --- | --- | --- |
| 元素定位数据 | 指认、保存页面/frame/shadow/元素路径 | 读取同样语义，在自己的浏览器中定位 |
| 值来源 | 账号库解析器，执行时读取或生成值 | 用例数据、环境变量、测试专用凭据解析器 |
| 基础填写结果 | 逐条状态与错误码 | 判断是否满足用例前置条件 |
| 业务行为与断言 | 本期只做到填字段 | 点击、提交、导航编排、等待业务条件、断言 |
| 测试运行 | 不建设测试平台 | 浏览器生命周期、并行、重试、数据清理、报告和 CI |

首版尽量把纯数据类型、配置校验、定位规则与 Tauri 调用分开组织；不急着抽成跨仓库公共包。
以后先由独立项目实现协议适配，真正有两个消费者且语义稳定时，再考虑共享库。

### 8.2 建议的便携导出形式

本地 `ValueRef` 在导出时映射为 `inputKey`，例如 `login.username`、`login.password`、`tenant.code`。
导出包含所需输入名和敏感性提示；独立项目用自己的数据提供器赋值，不需要读取 Switchboard 的账号库。

```json
{
  "format": "switchboard.field-bindings",
  "schemaVersion": 1,
  "requires": ["css-root-v1", "fill-text-v1"],
  "inputs": [{ "key": "tenant.code", "sensitive": false }],
  "bindings": [
    {
      "id": "binding-uuid",
      "inputKey": "tenant.code",
      "target": {
        "page": {
          "origin": "https://console.example.com",
          "pathname": "/login",
          "hashRoute": null,
          "queryEquals": {}
        },
        "contextPath": [],
        "locator": { "kind": "css", "value": "input[name=tenantCode]" },
        "expected": { "tag": "input", "type": "text" }
      },
      "fill": { "trigger": "manual", "overwrite": "empty-only", "events": ["input", "change"] }
    }
  ]
}
```

这是将来可实现的交换格式草案，本轮不创建导出器、JSON Schema 实现或测试工程。
`requires` 只列配置实际使用的能力；包含 iframe 或 Shadow DOM 路径时分别增加 `frame-path-v1`、`shadow-path-v1`。
消费者必须拒绝不支持的主版本或必需能力；不能忽略未知字段后“尽量执行”，从而改变填写目标或权限范围。
跨环境域名映射由独立项目显式提供并验证，不能直接去掉 origin 检查。测试凭据不复用生产账号的登录态。

### 8.3 不绑定某个浏览器工具

后续可以评估 Playwright、WebDriver 或其他执行器。原生 CSS 的 root 边界、Shadow DOM 穿透、可见性判定与输入事件行为可能不同，
所以复用的是数据与明确语义，需要适配层，不保证复制一个 selector 字符串就得到相同行为。

如果将来还需要自动化验证 Switchboard 自身，Tauri 官方当前提供 WebdriverIO 服务方案；macOS 可走嵌入式 WebDriver，
直接使用传统 `tauri-driver` 的平台覆盖不同。这个选择需另做验证，不能从 Playwright 能控制普通网页推断它能直接控制当前 WKWebView。
本项目目前没有接入这些测试插件。[参考：Tauri WebDriver](https://v2.tauri.app/develop/tests/webdriver/)

## 9. 后端和页面权限边界

主窗口的新命令可按职责拆为：开始指认、取消指认、保存/列出/删除绑定、执行/取消填写、读取运行状态。
名称和签名待实现阶段确定，新增命令需同步更新 [main-window.toml](../src-tauri/permissions/main-window.toml)。

远端页面只新增必要的“报告选中目标”和“报告填写结果”回传权限，不能获得读取账号、列绑定、选择任意值来源或执行任意脚本的能力。
后端根据调用者 webview 身份确定所属账号，再核对短期 pick/run ID、文档代次、目标和当前状态。
ID 用于关联任务和拒绝迟到消息，不把页面可见的 ID 当作能够抵御目标页面的秘密令牌。

跨帧通信继续遵循：定位广播不带值，值只定向发给通过校验的 frame，固定 targetOrigin；null origin 不允许领取敏感值。
仅校验“同站”不够替代实际 iframe 路径校验。首版不扩大跨站权限，也不修改 CSP 来允许任意导入脚本。

普通状态日志只记录绑定/运行 ID、结果码和耗时；地址按页面规则表示并脱敏，默认不采集截图、HTML 或输入框内容。
详细安全约束仍以 [ENCRYPTION.md](ENCRYPTION.md) 为准。

## 10. 实现拆分与复杂度

| 阶段 | 产物 | 复杂度与主要依赖 |
| --- | --- | --- |
| A：方案收敛 | 确定账号范围、自动触发、首版控件、交换格式方向 | 本轮文档阶段；不实现功能 |
| B：技术验证 | 主文档/跨帧目标识别、唯一匹配、回执关联、导航取消 | 风险最高，应先用自建假页面验证，不先接生产账号 |
| C：数据与执行基础 | 附加字段 ID 迁移、绑定存储、来源解析、顺序执行、状态回执 | 中等；影响账号编辑、打码恢复与备份兼容 |
| D：产品闭环 | 选择输入框、关联字段、保存/试填、管理绑定、自动填写 | 中等；依赖 B/C，不使用覆盖原生网页的 HTML 弹层 |
| E：便携导出 | 版本化交换格式、输入映射、导入校验 | 可后置；先让首版真实使用验证协议是否稳定 |
| 独立项目 | 自动化测试框架、流程与报告 | 另开项目、另排范围，不计入 Issue #1 |

不建议承诺为“一次 UI 小改”。主要不确定性是动态 iframe、SPA 导航与真实网站受控输入框的行为。
开发顺序应先证明这些部分，再扩展界面；技术验证失败时缩小支持范围并更新文档，不以静默误填作为兼容手段。

## 11. 开工后的验证关卡与验收案例

这里定义预期行为，**本轮没有编写或运行新增自动化测试**。本仓库已有功能级检查继续用于避免回归；用户规划的自动化测试产品在独立仓库建设。

### 必须先验证的技术关卡

1. 两个同 origin iframe 都含相同 selector，只允许选中的那一条路径收到值。
2. 跨源 iframe 逐层重建路径；iframe 与 open Shadow DOM 交错时可定位；无法证明路径时明确失败。
3. 导航前发出的定位或赋值回执，不能推进导航后的任务。
4. React/Vue 重渲染后可区分“脚本已派发”和“值实际被接受”。
5. 锁定时取消排队任务；Issue #2 保留的页面可以刷新，但不继续解析账号密码。

### 用户验收矩阵

| 场景 | 预期 |
| --- | --- |
| 为一个页面的账号、密码、企业编号分别建立绑定 | 保存后重开，启用自动的字段填入，手动字段等待用户操作 |
| 先点网页框，再选择左侧“企业编号” | 关联准确，保存前不会自动写入 |
| 账号和密码位于不同 frame | 分别定位，不要求同一帧同时存在两个框 |
| 修改字段值、名称或排序 | 同一绑定读取最新值，名称和排序不影响目标 |
| 删除字段再新增同名字段 | 旧绑定失效，不自动绑定到新字段 |
| 用户已经输入不同内容 | 自动模式跳过；主动覆盖要由用户选择 |
| 相同 selector 对应两个可见候选 | 报多命中，不任选一个填写 |
| 进入修改密码页或另一账号/站点 | 页面条件不符时不填，不因“同平台”放行 |
| 目标晚出现、永不出现或不接受值 | 分别成功、超时、明确失败，不永久显示处理中 |
| 填写中切账号、切页签、关闭或导航 | 不串号、不改为填写新激活页；失效任务返回取消/过期结果 |
| App 锁定且会话保活 | 保留页面，停止新的取值与绑定执行 |
| 导出供独立项目使用 | 只有定位、策略、输入引用；没有凭据与登录态 |
| 升级旧库、再次解锁、复制账号、导入备份 | ID 稳定；迁移可重复；原数据保留；绑定归属正确 |

验收只证明填写功能符合约定。测试项目还需要独立验证提交后的登录结果、业务状态和服务端数据。

## 12. 讨论结束的条件

开工前收敛这几项即可，不需要先把整个测试平台设计完：

1. 绑定默认按账号保存，还是本期就需要平台共享与账号覆盖。
2. 自动/手动模式的默认值，以及附加字段、TOTP 是否默认自动。
3. 是否接受首版聚焦文本输入，不自动点击提交。
4. 是否接受先稳定协议，便携导出随后实现，自动化测试另立项目。

本轮文档完成后保留在讨论状态，依据上述选择修订，再进入功能实现。

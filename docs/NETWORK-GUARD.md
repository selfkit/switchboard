## 1. 要解决什么

阿里云日志服务等控制台功能，因政策原因**不允许从中国大陆以外的网络访问**。用境外网络打开，轻则功能不可用、重则触发账号风控（异地登录告警、临时封禁）。

Switchboard 是"一键打开各家云控制台"的工具，正好是最容易踩这个坑的地方——用户开着代理，随手点一下账号，页面就在境外出口打开了。

**目标**：打开账号页面前判断出口所在地区，非中国大陆时按用户设定的策略处理。

## 2. 允许范围：只有中国大陆

| 地区 | ISO 码 | 是否允许 |
|---|---|---|
| 中国大陆 | `CN` | ✅ 允许 |
| 香港 | `HK` | ❌ 不允许 |
| 澳门 | `MO` | ❌ 不允许 |
| 台湾 | `TW` | ❌ 不允许 |
| 其它任何地区 | — | ❌ 不允许 |

**出口归属只允许 `{CN}`；若大陆出口同时检测到外网隧道，仍按网络异常处理。**

### ⚠️ 港澳台的判定陷阱

国内的 IP 库习惯把港澳台放在 `country = "中国"` 之下，用 `province` 区分：

```json
{"country": "中国", "province": "香港"}     ← 这是香港，必须拦
{"country": "中国", "province": "重庆市"}   ← 这是大陆，放行
```

**只判 `country == "中国"` 会把香港放进来**，直接违背需求。所以：

- 优先使用返回 **ISO 码**的数据源（实测 `ip-api.com`：香港 IP → `HK`、台湾 IP → `TW`、大陆 IP → `CN`，区分正确）
- 使用中文文本数据源时，`country == "中国"` **还必须**满足 `province` 不落在拒绝名单里：
  `{香港, 香港特别行政区, 澳门, 澳門, 澳门特别行政区, 台湾, 台湾省, 臺灣, Hong Kong, Macao, Macau, Taiwan}`
- 两条规则都不满足 → 按**境外**处理（保守方向）

### 已实测坐实（2026-09-20）

用支持查任意 IP 的 `https://kimmking.cn/ips?ips=...` 验证，结果如下：

| 地区 | 测试 IP | 返回 |
|---|---|---|
| 大陆（南京） | `114.114.114.114` | `中国,江苏,南京` ✅ |
| 大陆（杭州） | `223.5.5.5` | `中国,浙江,杭州` ✅ |
| **香港** | `219.76.10.1` | **`中国,香港,`** ⚠️ |
| **澳门** | `202.175.3.8` | **`中国,澳门,`** ⚠️ |
| **台湾** | `168.95.1.1` | **`中国,台湾,`** ⚠️ |
| 美国 | `8.8.8.8` | `美国,加利福尼亚州,圣克拉拉` ✅ |

**港澳台全部返回 `country = 中国`。** 这不是理论风险，是实锤：
照直判 `country == "中国"` 会把港澳台全放进来，正好违背需求。

所以 §2 那条"country + province 双重校验"是**必需项，不是保险措施**。

## 3. 一个必须先讲清楚的前提：代理分流

开发机上的实测，同一时刻、同一台机器：

| 探测服务 | 看到的出口 IP | 判定国家 |
|---|---|---|
| `r.inews.qq.com`（国内） | `203.0.113.79` | 🇨🇳 中国 重庆 |
| `myip.ipip.net`（国内） | `203.0.113.79` | 🇨🇳 中国 重庆 |
| `ip-api.com`（境外，HTTP） | `198.51.100.69` | 🇳🇱 荷兰 |
| `cloudflare.com/cdn-cgi/trace`（境外，IPv6） | `2407:cdc0:...` | 🇯🇵 日本 |

**三个不同国家，而且都没错。** 根因：

```
环境变量  HTTP_PROXY / HTTPS_PROXY = http://127.0.0.1:7897
系统代理  HTTPEnable=1, HTTPSEnable=1 → 127.0.0.1
```

本机跑着**规则分流代理**（Clash 这一类）：国内域名直连、境外域名走境外节点。所以"探测哪个服务"直接决定"得到哪个答案"。

### 这推翻了功能的原始命题

原需求是「判断当前系统网络是不是中国网络」。但在分流代理下，**不存在"当前网络"这个单一事实**——同一时刻不同目标走不同出口。

**正确的问题是：访问阿里云控制台时，出口在不在中国大陆。**

好消息是这个问题可以准确回答：内嵌的 WKWebView 走 **macOS 系统代理**，和探测请求受同一套分流规则约束。所以只要**探测服务的分流归类和目标站点一致**（都被判为"国内直连"），探测结果就能代表真实访问路径。

### 由此定下三条硬规则

1. **只用部署在中国大陆的探测服务**。境外服务会被分流到境外节点，必然误判——用 Cloudflare 的话，用户在重庆自己家里就会被拦。
2. **只用 HTTPS**。`ip-api.com` 免费版只有 HTTP（实测 HTTPS 返回 403），明文响应可被中间人伪造，等于这道闸形同虚设。
3. **检测到代理时，在界面上说明**："当前开着代理分流，检测结果代表探测请求的出口；若代理对阿里云单独设了规则，实际路径可能不同。"

### 3.5 开了 VPN 必须测准 —— 这条靠什么保证

这是整个功能的命门。**如果探测请求和 WebView 走的不是同一条路，这道闸就是摆设**：
用户开了全局 VPN，探测绕过代理看到国内 IP 判「放行」，而 WebView 走 VPN
真的从境外访问了阿里云——比没有这个功能更糟，因为它给了虚假的安全感。

#### 保证来自"共享路由命运"，不是"看到真实 IP"

内嵌的 WKWebView 走 **macOS 系统代理**。只要探测请求也走系统代理，
那么**探测看到什么出口，阿里云就会看到什么出口**——两者必然一致。

已验证：`reqwest 0.13.5` 的 **default features 包含 `system-proxy`**
（→ `hyper-util/client-proxy-system` → `system-configuration`，已在 `Cargo.lock` 中）。
也就是说 Rust 侧的 HTTP 客户端**默认就读 macOS 系统代理**，和 WebView 同路。

> ⚠️ **实施红线：绝对不能给探测用的 client 调 `.no_proxy()`，
> 也不能关掉 reqwest 的 `system-proxy` feature。** 一旦关掉，探测就绕过 VPN，
> 整个功能立刻失效且无声无息。这条要写进代码注释。

#### 覆盖的三种真实场景

| 网络状态 | 探测请求走哪 | WebView 走哪 | 探测结果 | 判定 | 正确吗 |
|---|---|---|---|---|---|
| 不开代理 | 直连 | 直连 | 国内 IP | 放行 | ✅ |
| **全局 VPN / 全局代理** | **走 VPN** | **走 VPN** | **境外 IP** | **拦截** | ✅ |
| 分流代理（国内域名直连） | 直连 | 阿里云同样直连 | 国内 IP + 外网可达 | 按异常处理 | 可能误拦，允许单次确认继续 |
| 分流代理（规则把阿里云也甩出去） | 直连 → 国内 IP | 走境外 | 国内 IP + 外网可达 | 按异常处理 | ✅ 避免误放行 |

国内 IP 探针无法判断目标站点是否也走直连，因此只要外网探针可达就按异常处理。
这会拦住确实走大陆出口的目标站点；用户可单次确认继续。**更精确的办法见下。**

#### 更准的做法（留作后续，不在本期）

真正无懈可击的探测是：**用目标站点自己的域名去问出口**。
比如阿里云的 `https://.../getIp` 之类接口——请求走的就是阿里云的分流规则，
测出来的就是访问阿里云时的真实出口。

不在本期做的原因：得为每个平台找一个"回显调用方 IP"的接口，
维护成本高，而且这类接口本身不稳定。本期先用通用探测覆盖 VPN 全局这个主场景。

#### 另外：VPN 未必是代理

WireGuard、公司 VPN 客户端这类**工作在网络层（tun 设备）**，不经过系统代理设置。
这种情况下**所有**流量（包括探测）都走 VPN，探测自然测得准，不用特殊处理。

需要担心的只有"应用层代理 + 客户端不读系统代理"这一种组合，而上面已经排除了。

### 3.6 第二个信号：外网可达性

只测出口归属不够，有个盲区：**分流代理把阿里云单独甩到境外节点**时，
探测（走国内服务、被判直连）看到的是国内 IP，测不出来。

补第二个信号：**本机能不能直接访问外网**。大陆的普通网络访问不了 Google，
能通就说明有隧道在跑。

#### 实测（开发机，Clash TUN 模式）

| 探测 | 方式 | 结果 |
|---|---|---|
| A 出口归属 | 走系统代理 | `203.0.113.79` 中国重庆 |
| B 出口归属 | **强制 `--noproxy`** | `203.0.113.79` 中国重庆（**和 A 一样**） |
| C 外网可达 | 强制 `--noproxy` 访问 google/gstatic/youtube | **全部 204，通** |

#### 两条结论

**① `no_proxy` 绕不过隧道。** A 和 B 结果一致、但 google 直连可达，
说明本机跑的是 **TUN 模式**（在网络层接管），代理设置层面的"强制直连"对它无效。

> 所以「探测本机物理网络」这条路**不可靠**，不能作为独立信号。
> 原计划的"双路径对比（代理路径 vs 直连路径）"在 TUN 下退化成同一条路，**放弃**。

**② 外网可达性是可靠的隧道探针。** 它不关心走哪条路，只问结果：
能通外网 = 有隧道（或人在境外）；不能通 = 典型大陆网络。

#### 探测目标

`https://www.google.com/generate_204` —— 正常返回 `204` 且响应体为空，
是最轻量的可达性探针。备选 `gstatic` / `youtube` 同款接口（实测三个都通）。

超时 **2 秒**。测不通不代表失败，**测不通本身就是结果**（说明是大陆网络）。

#### 合并判定

| 出口归属 | 外网可达 | 推断 | `block` 模式下的处置 |
|---|---|---|---|
| 🇨🇳 大陆 | ❌ 不通 | 纯大陆网络，无隧道 | ✅ **放行**（最干净的状态） |
| 🇨🇳 大陆 | ✅ 通 | **有隧道在跑**，目标站点实际出口不能仅凭大陆探针判定 | ❌ **按网络异常拦截**；`warn` 模式弹框确认 |
| 🌍 境外 | ✅ 通 | 全局 VPN，或人在境外 | ❌ **拦截** |
| 🌍 境外 | ❌ 不通 | 境外的受限网络 | ❌ **拦截** |

**为什么「大陆 + 有隧道」也处理**：国内探针显示大陆 IP，只能说明探针域名走大陆出口；
目标站点可能被代理规则单独分流到境外。按用户要求，这种状态进入与境外出口相同的
拦截 / 提示流程，并在界面上说明判定依据；不能宣称目标站点已经确定走境外。

> 残余限制：仅凭通用探针无法确认某个目标站点的实际出口，
> 因此检测到分流隧道时保守拦截；需要直连目标站点时可单次确认继续。

## 4. 三种模式

| 模式 | 行为 | 适合谁 |
|---|---|---|
| `block`（**默认**） | 境外出口或检测到分流隧道时**拦截**，不打开页面。给一个「仍要继续」的逃生口，每打开一个账号都要单独确认；确认后 30 分钟内哨兵不断开、不再问 | 默认。政策红线，默认从严 |
| `warn` | 境外出口或检测到分流隧道时弹确认框，问"是否继续"，选继续就正常打开 | 知道自己在干什么、偶尔需要绕过 |
| `off` | 完全不检测，不发任何探测请求 | 不需要 / 不想让 App 联网探测 |

**默认 `block`**，对应需求里的"默认开启"。但有一条例外不可动摇：

> **判定为「未知」时，任何模式都不拦截。**
>
> 探测失败的原因通常是断网、服务挂了、超时——不是"用户在境外"。因为探测不到就把人锁在门外，是把工具变成障碍。未知时放行，并在界面上留一条提示。

## 5. 检测方案

### 5.1 判定结果模型

```
RegionVerdict {
    origin:  Mainland | Outside { country, region } | Unknown { reason },
    tunnel:  bool,        // 外网是否直接可达 = 是否存在隧道
    proxy:   bool,        // 系统是否配置了代理（scutil / 环境变量）
}
```

放行与否看 `origin` 和 `tunnel`（§3.6 的合并判定表）：`Outside` 拦截，
`Mainland + tunnel` 也按网络异常处理，`Unknown` 不拦截。`proxy` 仅用于提示。

### 5.2 探测端点（基于实测选型）

| 端点 | 实测延迟 | 协议 | 结论 |
|---|---|---|---|
| `https://r.inews.qq.com/api/ip2city` | **302ms** | HTTPS | ✅ **主**。国内直连，最快，返回 `country` + `province` |
| `https://myip.ipip.net/json` | 1244ms | HTTPS | ✅ **备**。返回 `["中国","重庆","重庆","","联通"]` |
| `http://ip-api.com/json/` | 922ms | **仅 HTTP** | ❌ 否决。明文可伪造；且被分流到境外，实测返回"荷兰" |
| `https://www.cloudflare.com/cdn-cgi/trace` | 787ms | HTTPS | ❌ 否决。被分流到境外，IPv6 判成 `loc=JP` |
| `https://api.ip.sb/geoip` | — | HTTPS | ❌ 返回 403 |
| `https://ipapi.co/json/` | — | HTTPS | ❌ 免费额度被限流 |
| `https://kimmking.cn/ips?ips=…` | 216–305ms | HTTPS | ⭕ **不能当探测用**，见下 |

#### 为什么 kimmking.cn 不作为探测端点

它**不报调用方自己的 IP**——不带参数直接返回 `400 Bad Request`，必须显式传 IP 进去。
也就是说它是个**分类器**，不是"查我的 IP"服务，单独用不了。

但它有两个别的用处，都保留：

1. **交叉校验**：探测拿到出口 IP 后，可以再喂给它做第二次独立判定（见 §5.3）
2. **测试夹具**：能查任意 IP，港澳台那几条判定规则靠它才验得了（见 §2）

实测健壮性：

| 输入 | 返回 | 处理方式 |
|---|---|---|
| 正常 IPv4 | `"中国,江苏,南京"` | 正常解析 |
| 非法字符串 | `null` | **按未知处理，不可当成"非中国"** |
| IPv6 | `null` | 不支持 IPv6，落回 §10 的双栈缺口 |
| 内网地址 | `"IANA,,"` | 按未知处理 |

#### 路由敏感 vs 路由无关（选型的根本依据）

| 类型 | 例子 | 走哪条路影响结果吗 |
|---|---|---|
| **报「我的 IP」** | qq、ipip、cloudflare、ip-api | **敏感**。走代理就报代理出口——这正是实测出现 CN/NL/JP 三个答案的原因 |
| **查「指定 IP」** | kimmking | 无关。传什么 IP 判什么，跟自己走哪条路没关系 |

**探测必须用「报我的 IP」这一类，且必须选国内直连的**，否则测到的是代理出口不是真实出口。

附带证据：`kimmking.cn` 在本机解析到 `198.18.0.174`（Clash 一类工具 fake-ip 模式的保留段，
查它自己返回 `IANA,,`），说明这个域名**是走代理的**。对分类器没影响，
但如果它是个"报我的 IP"的服务，结果就废了。

> 端点会失效、会改格式。这份名单**存在数据库里可改**（复用现有的 `meta` 表），
> 不硬编码——跟「平台适配配置」同一个思路，失效了不用重新发版。

### 5.3 判定流程

```
                    ┌─ 模式 = off ─→ 直接放行，不发任何请求
                    │
   打开账号页面 ────┤
                    │
                    └─→ 读缓存（10 分钟内有效？）
                            │有 ──→ 用缓存结果
                            │无
                            ↓
                      并发请求「主 + 备」两个端点，各 3 秒超时
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
         两个都成功      只有一个成功      都失败
              │             │             │
        ┌─────┴─────┐       │             ↓
      一致        不一致     │        Unknown(网络不可达)
        │           │        │             │
        ↓           ↓        ↓             ↓
     用该结果   取「更保守」 用它       ★ 一律放行
                 的那个                  + 顶部提示
```

**"不一致取更保守"**：一个说大陆、一个说境外 → 按**境外**处理。宁可多问一次，不可漏放一次。

#### 两阶段：先定 IP，再定归属

主备端点除了给出归属，还会回带**它们看到的出口 IP**（qq 的 `ip` 字段、ipip 的 `data.ip`）。
利用这一点把判定拆成两步：

```
阶段一「我的出口 IP 是什么」   主备端点（国内直连）→ 203.0.113.79
阶段二「这个 IP 属于哪里」     ① 主备端点自己的答案：中国,重庆
                              ② 可选：喂给 kimmking 独立复核
```

**好处是让所有数据源判定同一个 IP 字符串**，而不是各自判各自看到的出口。
实测本机三个服务看到三个不同 IP（203.0.113.79 / 198.51.100.69 / 2407:cdc0:…），
不统一成同一个 IP 的话，"交叉验证"验的根本不是一回事。

> 另一条佐证：同一个 IP `198.51.100.69`，`ip-api` 说荷兰、`kimmking` 说日本。
> 单一数据源不可信，这是第二个例子。

### 5.4 缓存与轮询

- 结果缓存 **10 分钟**，存内存（进程退出即失效）
- 用户在设置页点「重新检测」可立即刷新
- **常驻哨兵按设置的间隔强制探测**，结果覆盖缓存；默认每 2 小时，可选 1/5/15 分钟、1/2 小时或 1 天

> ⚠️ 原设计写的是"不自动轮询，避免后台持续对外发请求"，**已推翻**（见 §6）。
> 每轮约 3 个探测请求（两个 IP 端点 + 一个外网探针）；默认约 3 次/2 小时，选 1 分钟时约 180 次/小时。
> 免费 IP 服务有被限流的可能；真撞上了，端点是可配置的（§5.2），换一个即可。

### 5.5 超时

单端点 **3 秒**，两端点并发，总耗时上限 ~3 秒。超时按 `Unknown` 处理（放行）。

> 3 秒是拍的：实测最快端点 302ms、最慢 1244ms，3 秒能覆盖慢速网络，
> 又不至于让用户点一下账号傻等太久。实施后按真实体感再调。

## 6. 拦截点

两处，管的是两件不同的事。

**开门那一下**：`switch_or_open_account`（`src-tauri/src/lib.rs`），在 `session::open_or_focus` 之前。
这是"打开/切换账号页面"的唯一入口，主界面「一键登录」、会话页左栏、⌘K 快捷切换全都汇到这里，在别处加等于漏。

**解锁账号库**：`unlock` 验证密码后读取加密设置，强制重测网络；境外出口或分流隧道命中时不把数据库连接交给 `Vault`，前端提示并停止进入账号库。
跟打开账号页一样给逃生口（`force`）：block 模式是不显眼的「仍要解锁（不记住）」，warn 模式是「继续解锁」。
不给的话会形成死结——检测模式存在加密库里，误判时（比如企业专线出口在境外）连"改成仅提示/关闭"都得先解锁，
最后只剩敲终端命令清库。放行的只是本地读库，之后打开每个账号页照样过检测，运行中的页面照样受哨兵管。

**运行途中**：`region_patrol`，按用户设置的间隔巡检。顶栏手动检测也走同一处置路径。

### 原设计的这一条已被推翻

> 已经打开的页面**不做二次拦截**——网络中途切换时强行关掉用户正在操作的页面，破坏性大于收益。

推翻的理由：这条只在"页面被关掉不可恢复"的前提下成立。但**切断不等于关闭**——
导航到 `about:blank` 就能让页面一个请求都发不出去，而 webview 和它的 cookie 仓原封不动，
恢复时导航回去即可，登录态一点不丢。前提不成立，结论就不成立。

而原设计漏掉的风险是实打实的：只在开门时查一次，等于只管了那一瞬间。
用户开着阿里云控制台，VPN 自动重连 / 分流规则变了 / 换了 Wi-Fi，页面会一直在境外出口上跑，
而这正是整个功能要防的事。

### 处置矩阵

代码在 `lib.rs` 的 `decide()`，四个输入（模式 × 是否需要处理 × 是否已切断 × 是否刚翻转）：

| 模式 | 需要处理 | 已切断 | 刚翻转 | 动作 |
|---|---|---|---|---|
| block | 是 | 否 | — | **切断**所有页面 + 弹框告知 |
| block | 是 | 是 | — | 什么都不做（别每分钟重切一次） |
| warn | 是 | 否 | 是 | 弹框问用户要不要断 |
| warn | 是 | 否 | 否 | 什么都不做（别每分钟骚扰一次） |
| 任意 | 否 | 是 | — | **接回**所有页面 |
| off | — | — | — | 连探测请求都不发 |

三条容易写错、已用单测钉死的：

1. **切断前必须先抄 cookie** —— 导航会丢掉内存里的会话态
2. **回到大陆无条件接回** —— 漏了这条，用户关掉 VPN 后会永远卡在空白页，且看不出是被谁断的
3. **恢复走 `recheck_and_restore`，不提供裸的 restore 命令** —— 那等于给前端一个
   点一下就能绕过拦截的开关。必须后端重新探测、确认回到大陆才接回

## 7. 界面设计

### 7.1 设置页新增「网络区域检测」

```
┌──────────────────────────────────────────────────┐
│ 网络区域检测                                      │
│ 阿里云日志等服务因政策原因不允许境外访问。          │
│ 打开账号页面前会检测出口所在地区。                  │
│                                                   │
│  ● 开启拦截    检测到非中国大陆就不打开（推荐）      │
│  ○ 仅提示      每次询问是否继续                     │
│  ○ 关闭        不检测，也不发探测请求               │
│                                                   │
│  当前：🇨🇳 中国 · 重庆（联通）        [重新检测]    │
│  ⚠️ 检测到系统代理，结果代表探测请求的出口          │
└──────────────────────────────────────────────────┘
```

- 当前状态实时展示，**用户能自己核对准不准**——这比什么都重要，误判时他一眼看得出
- 检测到代理时才显示那行 ⚠️

### 7.2 拦截弹层（`block` 模式）

```
┌────────────────────────────────────────┐
│ 检测到境外网络                          │
│                                         │
│ 当前出口：🇭🇰 中国香港                  │
│ 账号：阿里云 · 直播App - 推流服务        │
│                                         │
│ 阿里云日志等服务不允许从中国大陆以外     │
│ 访问，强行打开可能触发账号风控。         │
│                                         │
│ 检测到系统代理（127.0.0.1:7897），      │
│ 若你确认这个站走的是直连，可以继续。     │
│                                         │
│ [取消] [仍要继续（30 分钟内不断开）] [去设置] │
└────────────────────────────────────────┘
```

三个出口对应三种真实处境：**真在境外**（取消）、**误判**（继续）、**想改策略**（去设置）。

`warn` 模式用同一个弹层，只是措辞从"不打开"变成"是否继续"，主按钮换成「继续」。

**选了继续之后有 30 分钟宽限**（`FORCE_GRACE_SECS`）：这段时间里哨兵探到同样的异常不断开页面（block）、也不再弹框问（warn）。
没有它的话，block 模式下刚放行的页面一回到账号列表（会触发一次复查）就被断掉，「仍要继续」形同虚设。
宽限只管"不断、不问"，网络恢复照样把被断的页面接回来；过了 30 分钟按模式正常处理；锁定即作废。
打开**别的**账号不受宽限影响，照样要单独确认。

### 7.3 常驻状态指示

账号列表顶栏、会话页左栏各放一个小标识：

- `🇨🇳 大陆` — 正常，灰色小字，不打扰
- `⚠️ 境外` — 红色，点击展开详情
- `? 未知` — 灰色，点击可重新检测

让人**在点账号之前**就知道当前状态，而不是点下去才被弹窗打断。

## 8. 存储

模式设置存进**已有的 `meta` 表**（加密库里），不加新表：

| key | value | 默认 |
|---|---|---|
| `region_guard_mode` | `block` / `warn` / `off` | `block` |
| `region_probe_endpoints` | JSON 数组，探测端点列表（**决策 4：可改**） | 内置主备两个 |
| `region_watch_secs` | 自动巡检间隔，60–86400 秒 | 7200 秒 |

`region_probe_endpoints` 的结构，跟「平台适配配置」同一个思路——端点挂了、改了格式，
改这里就行，不用重新发版：

```json
[
  {
    "name": "qq",
    "url": "https://r.inews.qq.com/api/ip2city",
    "ip_path": "ip",
    "country_path": "country",
    "region_path": "province"
  },
  {
    "name": "ipip",
    "url": "https://myip.ipip.net/json",
    "ip_path": "data.ip",
    "country_path": "data.location.0",
    "region_path": "data.location.1"
  }
]
```

`*_path` 用点号路径从 JSON 里取值（数字段表示数组下标）。设置页提供一个编辑入口，
格式不合法时拒绝保存并保留原值——**别让人把自己配到打不开 App**。

检测结果**只存内存**，不落库——它是瞬时状态，重启后重新检测即可。

## 9. 隐私说明（必须写进设置页）

开启此功能后，App 会向**中国大陆的 IP 归属查询服务**发请求。需要向用户讲明：

- **发出去的**：一次普通 HTTPS 请求。对方能看到你的出口 IP（这是它的工作原理，任何网站都能看到）
- **不发出去的**：账号、密码、你要打开哪个平台——探测请求里一个字都没有
- **存下来的**：只有"大陆/境外/未知"这个结论和时间戳，在内存里，重启就没
- **外网可达性探测**会向 `https://www.google.com/generate_204` 发一次请求。
  这个接口只返回一个空的 204，不带任何内容；对方同样只能看到你的出口 IP
- **选 `off` 则一个请求都不发**

## 10. 局限与误报

写在这里，不藏着：

| 情况 | 后果 | 缓解 |
|---|---|---|
| **代理对目标站单独设规则** | 国内探针无法代表目标站点的出口 | §3.6 的外网可达性信号能测出隧道并按异常处理；逃生口保留 |
| **TUN 模式接管网络层** | `no_proxy` 失效，测不到本机物理网络 | 已放弃"双路径对比"方案，改用外网可达性（§3.6） |
| **双栈 IPv4/IPv6 出口不同** | 实测本机 IPv4 在重庆、IPv6 被判日本 | 探测强制走 IPv4；但浏览器可能优先 IPv6，**这是已知缺口** |
| **企业专线出口在境外** | 明明是国内公司却判境外 | 逃生口 + 可改成 `warn` 或 `off` |
| **IP 库数据过期** | 新分配的 IP 段判错 | 双端点交叉验证；端点可改 |
| **探测服务挂了 / 改格式** | 判定为未知 | 未知放行；端点存库可改，不用发版 |
| **用户手动点「仍要继续」** | 绕过拦截，之后 30 分钟哨兵不断开 | 这是设计意图——工具不能把人锁死；宽限只看时间，期间网络变得更糟也不会断（`ponytail:` 注释里记着升级路径） |

**这不是安全边界，是防呆。** 用户自己就能绕过（改设置、点继续、关掉功能）。它防的是"没注意到开着代理就点了账号"，不防蓄意规避。
